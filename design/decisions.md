# Design and technology decisions

| # | Decision | Why |
|---|---|---|
| D1 | Frontend: React + Vite (JSX), React Router, plain CSS with tokens | Small, fast to build, no CSS framework needed; matches the team's JavaScript-only rule. |
| D2 | Backend: Node 20 + Express 4, mysql2, zod | Same language as the frontend; zod validates every external input (CLAUDE.md). |
| D3 | Database: MySQL 8.4 in Docker Compose (host port 3307) | MySQL is not installed on the team's machines; `npm install` + `npm run dev` start it automatically. |
| D4 | Map: Leaflet with OpenStreetMap tiles darkened with a CSS filter, placeholder checkpoint coordinates | CARTO Dark Matter was planned, but its free tiles now answer with an "API KEY REQUIRED" watermark. OpenStreetMap needs no key; `VITE_MAP_TILE_URL` and `VITE_MAP_DARKEN` switch to another provider. Real coordinates are calibrated on site (WBS 4.1). |
| D5 | Visual direction (revised 2026-10-27): the app follows the second Figma Make prototype ("campusGO after prompt"): DHBW signal red and anthracite grey, light and dark theme, Source Sans 3, soft shadows, a red hexagon "GO" badge as menu button, full-width menu bars, red page-change stripe, diamond map pins, radar location check, read-first info page, player cards with six avatars, German and English, font size setting | The project manager preferred how this prototype feels. It replaces the first mix of "Arcade Night Campus" tokens and light panels. |
| D6 | The location-based game is only "inspired" by location games: no ball motif, no Pokémon or Persona imagery | Decision by the project manager. |
| D7 | Menu and quiz behaviour: the arena winner (a002, 86 to 73.5) gave the accessibility rules that are still used: page behind the menu is inert, Tab stays inside, arrow keys walk the bars, Escape closes, one server deadline with a timer that never shows "expired" for a frame, answers locked after one tap, no auto-advance. Its look (slanted trail, arcade tokens) was replaced by D5. Spec: [arena/menu-and-quiz-ui-spec.md](arena/menu-and-quiz-ui-spec.md) | The rules came from attack and defend rounds and are tested in `frontend/tests/menu.test.jsx` and `frontend/e2e/`. |
| D8 | Server authority for time, location and correctness; exact points kept in hundredths, rounded up once per user | BR22, R-02. |
| D9 | Resend cooldown for OTP is 30 s (was 60 s in the first spec) | Value in the build prompt; R-33 updated. |
| D10 | City expansion is a Could item only | Out of scope for the pilot. |
| D11 | Language (German or English), dark mode and font size (S to XL) are stored in the browser (`localStorage`) and applied through `data-theme`, `lang` and a `--fs` scale factor | Taken from the prototype; texts are written in English and translated by key (`frontend/src/de.js`, `de-extra.js`); a test fails when a text has no German translation. |
| D12 | The read-first info page is built (a Should item): three facts per checkpoint in the table `checkpoint_facts`, shown after the location is verified and before the timer starts (R-62) | In the prototype; the start gate already allowed it. Facts in the seed are PLACEHOLDERs. |
| D13 | Not taken over from the prototype: replaying a cleared checkpoint (BR21 says a passed checkpoint is final), leaving a team (OP-06), the distance to a checkpoint (location is only read when a quest starts, BR12), error texts that reveal whether an invitee exists or is in a team (R-43), demo accounts and the browser mock-up frame | Business rules and privacy come first. |
| D14 | The city map zone is a locked tab on the map ("City zones: coming soon") instead of a separate page | Same Could item as D10, shown the way the prototype does. |
| D15 | Real checkpoint coordinates from the project manager's Google Maps links (Neue Mensa, Cafeteria, Bibliothek LIV, Campus Garden, Care.Box and Shop.Box merged to their midpoint, Building B, Building C, Parkplatz am Bildungscampus). Radius stays 50 m (OP-22); Mensa and CAS Cafe are about 30 m apart so their circles overlap. The map cannot leave the Heilbronn area (zoom 14 and up, bounds about 6 x 7 km) | The old coordinates were in the wrong place. Radii still have to be calibrated on site with real phones (WBS 4.1). |
| D16 | JavaScript only; Dart was considered and rejected | Dart would mean a Flutter rewrite or a second toolchain next to React and Node, with no benefit for this web app. |
| D17 | No region lock (a 150 km circle around Heilbronn was requested, then dropped) | The project manager decided it is not needed. |
| D18 | Admin area, account status, audit log, name filter and self-deletion (BR26 to BR31, proposals) in new files and migration 003 | Requested after the pilot rules; kept apart from the core files so the backend rewrite by Yuri can take them over (see [yi_heng/backend-handover.md](yi_heng/backend-handover.md)). |
| D19 | Place photos only from freely licensed sources (Wikimedia Commons), credit shown under every photo; Google Maps photos are not reused. Carousel moves on every 5 seconds and pauses on hover, focus, hidden tab and reduced motion | Google's photos are not licensed for reuse. Only generic Bildungscampus photos were found; none shows a single place (Mensa, library ...). The alt texts say "general view" and the photos must be replaced by the team's own pictures before the pilot. |
| D20 | Walking route: client only, OpenStreetMap foot router (`routing.openstreetmap.de/routed-foot`, override with `VITE_ROUTING_URL`), straight line when the router is offline | The position never leaves the browser (BR33). The public router has a fair-use policy; use an own router for real traffic. |
| D21 | Invitations keep the generic reply (R-43). The new BR32 caps members plus open invitations at 5 and the Team page shows the pending slot with a countdown | Gives the inviter visible proof without a new error that depends on the invitee. |
| D22 | Team ranking has one definition (`backend/src/services/team-ranking.js`): at least two active students and no administrator; score = rounded-up average of the active students | The same rule was needed in four places (board, profile, statistics, result); a team with an admin must never appear in a ranking (BR42, BR43). |
| D23 | Admin points are reset by deleting the admin's own attempts, answers and location checks | The points are a sum of attempts, so resetting only the total would let the next test fail on "passed checkpoint is final" (BR41). |
| D24 | A top-level `tests/` folder with a manifest and a runner (`node tests/run-all.mjs`) that restarts ALL suites on a failure; existing suites stay in place and are referenced | Chosen by a two-agent /arena run, see [yi_heng/test-architecture-spec.md](yi_heng/test-architecture-spec.md). |
| D25 | Python (pytest, pylint, black, requests, pymysql) is used for the black-box API, database, security, performance and regression tests; `@axe-core/playwright` for accessibility scans | Python tests exercise the system through the same interfaces as a client, independent of the JavaScript implementation. Both are development-only dependencies (CLAUDE.md asks for a reason per dependency). |
| D26 | Team leader = creator (`teams.leader_id`); the leader removes members, any member cancels an invitation, an admin can add students to any team (BR44 to BR46) | The project manager wants teams managed by the students and expired invitations fixable without database work. |
| D27 | Admin delete is soft and restorable until a second confirmation erases it; a student's own delete erases at once but is logged with the time (BR47) | Chosen by the project manager. `purged_at` separates "deleted" from "erased". |
| D28 | One map style per account, stored as JSON on the student and checked on the server; the default style leaves the theme colours alone (BR48) | Follows the student across devices and cannot be used to inject CSS (colours are normalised to `#rrggbb`). Light stays the default. |
| D29 | Quests are database rows that admins manage; each attempt copies the question count and pass mark; a used quest or question is archived, never erased (BR49) | Edits must not change running or finished attempts (BR21, R-24). |
| D30 | Question types MCQ and MULTI, multi-select judged by exact match, `attempt_answers` keeps every ticked option (BR50) | Exact match was chosen by the project manager; one row per ticked option keeps the history without a JSON column. |
| D31 | Google Maps links are read on the server, short links only on Google hosts over https with limited redirects; positions must be inside one shared map area constant (BR51) | The box must not become a way to reach other servers (SSRF), and a quest outside the visible map could never be found. |
| D32 | ~~Development login prints every code, has no throttle and asks for a new code after a rejected one (BR52)~~ Superseded by D35 on 2026-11-10 | The local `.env` throttle silently sent nothing after restarts, which looked like a broken login. |
| D33 | Optional 3D map with MapLibre GL JS and OpenFreeMap vector tiles next to the flat Leaflet map; flat stays the default, 3D is a per-device preference and a switch on the map; MapLibre is loaded only when the 3D map opens (trial, needs team approval) | Mapbox GL JS was considered but needs an account, a token and billing above the free tier, and is not open source. MapLibre (BSD-3) and OpenFreeMap (no key, OSM building heights) keep D4's "no key" choice. The LGL aerial photo is reused as a raster layer. The admin geofence editor stays flat, because circles are edited there. Without WebGL or when the style cannot load, the student is told and gets the flat map. |
| D34 | One set of map buttons for the flat and the 3D map (compass above zoom in 3D, with its slot kept free in 2D; an aerial/street switch, darker grey when the aerial photo is on; a 2D/3D switch that shows the view that is on, red for 3D); switching keeps place and zoom (2D to 3D keeps the north-up view and only tilts on the spot); the buttons sit below the header, whatever its height. Live location as a puck in the app's own look (white disc with a DHBW slate rim and a red chevron, a light grey disc on a dark map; not a navigation app's blue dot) whose chevron turns with the walking direction, else the compass or, without one, the gyroscope (lined up with the walking direction; screen rotation corrected); its accuracy circle, a sixth of the GPS accuracy, is a much lighter red on a light map; the map follows it closely (zoom about 20.1, 2.2 times as close as zoom 19; tiles are enlarged above the servers' last level up to zoom 21) until the student moves the map, and "Re-center" (a white button with slate text and the same chevron, light grey on a dark map, a red square while following; bottom left, on one line with the GO badge and the 3D map's credits button, which starts closed) flies back. The walking route starts at the live position, only the part ahead is drawn, a dotted curve leads from the visitor into its start, and a new route is fetched after a wrong turn (over 40 m off, at most every 20 s) (trial, needs team approval) | Two different button sets were confusing, and a switch that reset the view lost the student's place. The live position stays in the browser and is never sent to our server; only the route request goes to the OpenStreetMap router, as before. Location is watched at once only when the browser already allows it for the site; otherwise the first tap on Re-center asks, so the map never asks without a tap. A position outside the map area is not followed. |
| D35 | Real OTP e-mail always (Yuri's SMTP mailer), plus an admin switch *code preview* stored in `app_settings`: the same code is shown in a test inbox on the login page and printed in the terminal; on by default only in development (BR52) | Testing needs a login without a mailbox, deployment needs it off. A run-time switch avoids a redeploy; the code is kept in memory only, so the database still holds hashes. Preferred over a separate "mock mailer" because it guarantees the shown code is the e-mailed one. |
| D36 | The pilot checkpoints are seeded once (marker in `app_settings`); after that quests belong to the admins (BR55) | The seed ran on every `npm run dev` and reset admin values; a reset question count against an admin's time limit failed the `ck_checkpoint` CHECK, so the API never started and the web app showed only proxy errors. |
| D37 | Team order column `students.team_position` instead of reusing `team_joined_at` (BR54) | The admin can reorder a team without falsifying when someone joined; the leader hand-over follows the order. |
| D38 | Docker development stack: `docker-compose.yml` + `backend/Dockerfile.dev` + `frontend/Dockerfile.dev`, repository root as build context, only package manifests and source folders copied, `npm ci --ignore-scripts` inside Linux | Exactly the three files requested; copying only listed paths keeps a Windows `node_modules` (wrong native builds) out of the image without a `.dockerignore`. `npm run dev` keeps working because it starts only the `mysql` service. |
| D39 | Second pre-seeded, protected admin: the team's shared mailbox `dhbw.campusgo@gmail.com`. `ADMIN_EMAILS` is a comma-separated list (Yuri's implementation in preproduction, merged 2026-11-11; an empty value falls back to the default); both admins are seeded by `db:seed` and on every API start, and only these addresses may log in outside `heilbronn.dhbw.de` (BR26, BR37; exception to R-31, to be confirmed by the team) | So the team reaches the admin area without a personal school account. Yi Heng and Yuri built this in parallel; Yuri's version was kept (it was already in preproduction), with Yi Heng's tests, login-page hint and production settings adapted to it. The address `dhbw.campus@gmail.com` from the first draft was dropped. |
| D40 | Separate production Docker stack (`docker-compose.prod.yml`, `backend/Dockerfile`, `frontend/Dockerfile` with nginx) next to the development stack; settings in `.env.production` (ignored by git); the school's web server terminates HTTPS on our subdomain and forwards to one HTTP port; `TRUST_PROXY=2` (changed to 1 by D41) | The development stack (Vite dev server, code preview on, demo players, dev passwords, public MySQL) must not face the internet, and its Vite dev server and `localhost` origin block a real domain. Verified end to end on 2026-11-10 with a test mail server: built app, SPA routes, API through nginx, real e-mail login, Secure cookie, picture upload, restart persistence, only the web port published. |
| D41 | Production hardening before deployment (2026-11-12): nginx believes `X-Forwarded-For` only from `TRUSTED_PROXIES` (required, written to `set_real_ip_from` at container start) and passes exactly one visitor IP to the API (`TRUST_PROXY=1`); the port can be bound with `HTTP_BIND`; the API container gets only its own settings (no `env_file`, so never the MySQL root password); `scripts/backup-prod.sh` dumps the database and pictures nightly (R13); the API start and the admin dashboard warn while PLACEHOLDER questions, facts or descriptions are live (BR11) | With the port open and two trusted hops, a client reaching the port directly could send a new fake IP with every request and bypass the per-IP limits on login codes (BR01). A firewall alone is not reliable because Docker-published ports skip ufw. The backup and the placeholder warning close risk R13 and the "placeholder content goes live unnoticed" gap found in the review. |
| D42 | The team's question bank (Main Project Document pages 7 to 14) is the seed's default (`backend/src/db/question-bank.js`, seeded once with the marker `question_bank_v1`; untouched PLACEHOLDER questions in older databases are switched off, not deleted); the team's on-site photos are attached to their questions in a new table `question_images` with `shown = 'question'` (needed to answer) or `'answer'` (only after answering), and replace the Wikimedia stand-ins of Mensa, Library and Care.box/Shop.box; test databases keep the placeholder questions (2026-11-12) | Many photos show the answer (a building number, a shelf label, a price tag), so showing them with the question would give the answer away; after answering they teach where things are. Switching off instead of deleting keeps old attempts valid (BR23). The automated tests pick right answers by the placeholder marker, so they keep their own bank. All photos are re-encoded without metadata (no GPS position). |
| D43 | Precise location (2026-11-12): the location check averages the phone's precise readings over a few seconds (weighted by 1/accuracy², cached readings and outliers left out, the accuracy of the best single reading and the age of the oldest are sent), the screen shows the accuracy reached so far, distances are measured on the WGS84 ellipsoid (Vincenty) on the server, the map and the mock API, and the live map no longer counts a repeated or older fix | A single fix jitters by a few metres; averaging good readings halves that without claiming a better accuracy than measured. The sphere was 0.3 % short east-west at Heilbronn. The BR12 limits are unchanged. R-60 named Haversine, so the wording there was updated and needs the team's approval. |
| D44 | The live map restarts the browser's watch whenever it has been quiet for 2 s (a new watch starts with a fresh fix), so the ball gets a reading at least every 3 s (a restart still waiting gets 6 s; not while the tab is hidden; no one-off `getCurrentPosition`, which cannot be cancelled and blocked the next location check with a simulated position); the map style (BR48) gets two ball colours, `ball.body` and `ball.lines` (the lines colour also tints the direction wedge), with a ball in the preview and a matching ball in every preset (2026-11-13) | Requested by the project lead: the ball should stay close to the visitor and be customisable. Asking a second early covers the time a warm GPS takes to answer. Colours are CSS variables written only when they differ from the default, so the default ball is unchanged. |
| D45 | Quest texts and countdown (2026-11-13): the quest descriptions and read-first facts are written from the team's question bank so every normal question can be answered from them (hard questions only say where to look, they stay an on-site challenge); seeded once over the placeholders (marker `quest_content_v1`), which also sets Library and Building B to mixed so their multi-select questions are drawn. After the location check a 3-2-1 countdown runs; the server moves `start_time` and `expires_at` back by 3 s so no quiz time is lost, and sends no questions before `start_time` (R-66, needs the team's approval). The mock serves a generated copy of the bank (`npm run questions:sync`) | Placeholder facts gave students nothing to read; 2 of 69 questions could never be drawn; a countdown that ate the timer would cost points |
| D46 | Fluid live ball (2026-11-13): the ball follows the position every frame (eases towards the newest reading, walks on at the measured pace for at most 2 s between readings, sleeps when still) instead of a 350 ms glide per reading; the filter, walking direction and compass are more sensitive (drift 30 m²/s, 4 m, 0.5 m/s, 2°) | The ball stood still between readings and small moves were smoothed away, so it lagged behind the visitor |
